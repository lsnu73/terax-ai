# 应用更新

- 最后校验：2026-11-08
- 状态：已覆盖

## 1. 业务需求

应用启动后是否自动检查新版本由「设置 → 通用 → 启动 → 启动时自动检查更新」决定，默认开启。开启时，启动检查若发现新版本，不再弹出更新窗口，而是发一条消息（运行时通知中心 / toast，取决于用户的通知展示偏好），消息里的按钮直接打开「设置 → 关于」。用户到达关于页时，启动检查已经拿到的新版本信息被复用：更新按钮直接显示「安装 vX」，点击即下载并安装，不再经历「检查更新」阶段。

关闭该开关后，启动时不发起任何检查，用户仍可在关于页手动检查。Linux 客户端不自动下载安装：关于页的更新按钮打开 Release 页面，由用户自行取包。

## 2. 入口与调用链

- 设置项：`src/settings/sections/GeneralSection.tsx` 的启动分组渲染「启动时自动检查更新」开关，写入 `setAutoCheckUpdates`（`src/modules/settings/store.ts`），偏好键 `autoCheckUpdates`。
- 启动检查：`src/app/App.tsx` 在 `deferredUiReady` 后调用 `useStartupUpdateCheck(deferredUiReady)`（`src/modules/updater/useUpdater.ts`）；该 hook 等待偏好 `hydrated` 且开关为 true，再调用 `useUpdaterStore.getState().check()`。
- 检查实现：Windows/macOS 走 `@tauri-apps/plugin-updater` 的 `check()`（读取 latest.json，超时 `UPDATER_TIMEOUT_MS`）；Linux 走 `net_http_get` 请求 GitHub Releases latest API（10s 超时，与前端一致）。两者都遵循更新场景代理 `proxyForScenario(..., "updater")`。
- 通知：发现更新后 `source` 记为 `startup`，hook 用 `runtimeToast.info` 发消息，action 调用 `openSettings("about")`。
- 关于页：`src/settings/sections/AboutSection.tsx` 的 `useUpdater()` 读取同一全局 store；`available` 时按钮为「安装 vX」，点击 `install()`；`manual-available`（Linux）时点击打开 `status.info.releaseUrl`；其余情况点击 `check({ manual: true })`。
- 安装：`install()` 用 `update.downloadAndInstall` 上报 Started/Progress/Finished（下载请求同样带 `UPDATER_TIMEOUT_MS` 超时），完成后 `relaunch()`。

```text
启动
  -> App.useStartupUpdateCheck(deferredUiReady)
  -> 偏好 hydrated && autoCheckUpdates
  -> useUpdaterStore.check()
  -> plugin-updater / GitHub API
  -> status = available（source = startup）
  -> runtimeToast.info + 「前往关于」action
  -> openSettings("about")
  -> AboutSection.useUpdater() 读取同一 store
  -> 按钮「安装 vX」-> install() -> downloadAndInstall -> relaunch
```

## 4. 数据流与关键流程

1. 偏好 hydrated 后，`useStartupUpdateCheck` 只在 `enabled && hydrated && autoCheckUpdates` 时执行一次启动检查。
2. 非手动检查先读 `localStorage["terax:updater:last-check"]`，30 分钟内不重复检查；「已是最新」时写回时间戳，「发现更新」时不写，因此下次启动仍会检查。
3. `check` 把状态置为 `checking`；找到更新时写 `status: available`（或 Linux 的 `manual-available`）并记录 `source: startup`，否则写 `uptodate`。
4. 通知 effect 只订阅「可用版本号」这个原始值，避免下载进度等状态变化导致整个 App 重渲染；同一版本在一个应用会话内只提示一次。
5. 用户在关于页触发安装后，状态经 `downloading` → `ready`；成功后 relaunch。若用户手动检查，`source` 为 `manual`，不会触发启动消息。
6. 手动检查与启动检查共用同一 store，因此关于页始终显示当前真实状态，上传下载进度在切走再回来时也不会丢。

## 5. 对外接口

- 更新清单：Windows/macOS 读取 `src-tauri/tauri.conf.json` 配置的 latest.json；Linux 读取 `https://api.github.com/repos/lsnu73/terax-ai/releases/latest`。
- 通知 action：`{ label, onClick: () => openSettings("about") }`，由 `src/modules/agents/lib/types.ts` 的 `NotificationAction` 承载。
- 偏好：`autoCheckUpdates: boolean`（默认 `true`），存储于 Tauri store 偏好文件并通过 `terax://prefs-changed` 广播。
- 无新增 Tauri command、HTTP 接口或持久化文件。

- 本地节流键：`terax:updater:last-check`（localStorage）。

## 7. 已知限制与注意事项

- Linux 只提示并打开 Release 页面，不自动下载安装；原先弹窗里的发行版命令已随弹窗删除。
- 消息是否以 toast 形式出现取决于「通知显示方式」偏好；选择「仅通知中心」时只在铃铛历史里显示。
- 启动检查发生在主界面 `deferredUiReady` 且偏好 hydrated 之后，不阻塞启动；首屏之前不会出现检查进度或弹窗。
- 发现更新时不更新节流时间戳，因此同一版本会在每次启动重新检查并提示（一个会话内只提示一次）。
- 启动检查只检测、不下载；下载和安装必须由用户在关于页点击确认。
- 手动检查不触发启动消息，避免用户主动操作后又收到重复提醒。
- 检查与下载的 10s 超时是整请求超时（Tauri updater 的 `timeout` 选项覆盖从建连到响应体读完），下载安装包必须在 10s 内完成，慢速网络会失败进入 error 状态，用户可重试；超时语义的根因与取值依据见 lore [pitfalls/2026-11-08-更新器timeout覆盖整个下载请求.md](../../lore/pitfalls/2026-11-08-更新器timeout覆盖整个下载请求.md)。
