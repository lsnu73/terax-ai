# 大模型多厂商接入的配置驱动与请求参数合并

- 首次记录：2026-11-25 ／ 最近修订：2026-11-25
- 一句话总结：把“接厂商、加模型、调高级参数、切思考强度”收敛成一份可手改的 JSON，用固定顺序合并成请求体；坏配置只告警不崩溃，密钥不进文件。
- 适用场景：需要接入多家大模型厂商的客户端（聊天应用、IDE 助手、Agent 工具、自建模型网关），以及任何允许用户自定义请求字段的 HTTP 客户端。
- 阅读前提：知道 JSON、HTTP 请求体、系统密钥库三个概念；不需要了解任何具体项目的代码。

> **先读这里（TL;DR）**：配置文档是唯一事实来源，代码只保留少数协议适配器。参数按“厂商静态参数 → 模型静态参数 → 当前档位 → 兜底字段”的顺序合并，后者覆盖前者。静态参数与档位的空值表示“本层不写”，只有兜底字段的空值表示“删除该键”。传输层自有字段禁止用户覆盖。加载时宽容收敛：坏条目跳过并告警，不因一处笔误让全部模型不可用。密钥只存系统密钥库，配置文件只放账户名。

## 1. 要解决什么，为什么难

- **从一个具体事故说起**：团队每接一家模型厂商就要改一次代码、发一次版，用户想调一个频率惩罚系数也要等新版本；某次有人手工改配置文件时少了一个逗号，应用启动后所有模型全部不可用；还有人把密钥直接写进配置文件贴进工单，密钥随附件泄露。本文要解决的就是“接入与调参不依赖发版、坏配置不拖垮全局、密钥不落配置文件”这三件事。
- **成功长什么样**：
  - 新增一家同一协议族的厂商或模型，只改配置文件，代码与版本不变。
  - 设置页与手工编辑读写同一份配置，加载不因单点错误全盘失败。
  - 设置页预览的请求参数与真实发出的请求体完全一致。
  - 配置文件中搜不到任何密钥明文。
- **硬约束（带量级）**：
  - 合并函数是纯函数（同样输入必得同样输出、不读写外部状态）、同步，单次耗时小于 1 毫秒，界面可直接调用。
  - 代码中的厂商分支只允许出现在封闭的协议枚举对应的适配器里。
  - 配置读取失败时不得自动重写用户文件。
  - 密钥只进系统密钥库；配置文件只存账户名。
- **为什么直觉做法不行**：
  - 直觉做法一：为每家厂商写一个条件分支解析参数。坏在厂商数量增长后分支爆炸，且用户无法自行添加未预置的参数。
  - 直觉做法二：把各层配置字段级深合并。坏在上层写过的字段下层永远删不掉，用户无法表达“只改这一个字段”。
  - 直觉做法三：读到坏配置就抛错或自动重写。坏在一处笔误让全部模型不可用，或把用户唯一的手工副本抹掉。

## 2. 核心概念（逐个讲透）

**概念 A：配置文档是唯一事实来源**
- 是什么：厂商、模型、连接方式、共享参数、强度档位、默认模型都放在一份可手改的 JSON 里。
- 解决什么：把“接厂商”从改代码变成改数据；内置目录退化为“添加”动作的模板。
- 一个反例：厂商列表硬编码在代码里，用户想接一个自建网关只能等发版。
- 和下一个概念的关系：文档里的作用域决定谁覆盖谁。

**概念 B：作用域链（模型 → 厂商 → 全局默认）**
- 是什么：参数和档位可在厂商级共享，模型级只写差异；模型没写就向上找，全局层只在产品提供全局默认时存在。
- 解决什么：避免每个模型重复抄同一组参数，同时允许个别模型偏离。
- 一个反例：十个模型各抄一份相同参数，改一处要改十处，且很容易漏。
- 和下一个概念的关系：作用域只决定“取哪份定义”，真正写进请求体由补丁计算完成。

**概念 C：请求体补丁与固定合并顺序**
- 是什么：把各层配置解析成一个键值补丁，再按固定顺序覆盖进请求体。
- 解决什么：让设置页预览与真实发送共用同一个纯函数，结果可复现、可测试。
- 一个反例：界面按一套顺序展示，传输层按另一套顺序合并，用户看到的不是实际发出的。
- 和下一个概念的关系：补丁允许空值和点号路径，需要明确的边界规则。

**概念 D：宽容收敛（加载即修复）**
- 是什么：读盘后把任意 JSON 收敛为合法配置，问题记入告警而不抛错。
- 解决什么：手工编辑出错时只损失出错条目，其余照常可用。
- 一个反例：一个非法枚举值触发异常，整个应用没有可用模型。
- 和前面概念的关系：它为 A、B、C 提供“永远可用的输入”。

**核心链路（快速认知）**：
`配置文件` →（收敛：丢未知字段、跳过非法条目、补默认值）→ `合法配置` →（解析：厂商参数 → 模型参数 → 档位取值 → 兜底字段）→ `请求体补丁` →（传输层深合并）→ `最终请求体`

## 3. 规则与决策（先给场景，再给结论）

### 3.1 规则总览

规则分三组：R1–R5 管“配置长什么样”，R6–R10 管“补丁怎么算”，R11–R12 管“配置坏了怎么办”。一次请求先由 R11 保证输入合法，再由 R6 顺序合并，途中由 R8 处理空值、R9 拦截受保护键、R10 处理嵌套路径。R2 的继承只决定取哪份定义，R6 的覆盖顺序决定最终取值；两者冲突时以 R6 的顺序为准。

### 3.2 规则组 A：配置模型

- **R1 当要接入新厂商或新模型时，只改配置数据，不在代码里增加厂商分支；否则每接一家都要发版，用户也无法自行扩展。**
  - 输入：新增一家兼容既有协议的厂商，或给已有厂商加一个模型。
  - 动作：在厂商列表新增条目，填协议标识、地址、认证方式、模型列表；必要时在模型级写差异参数。
  - 结果：重载配置后该厂商与模型可用，代码中不出现新厂商名。
  - 理由：厂商分支一旦写进代码，接第 N 家就要改 N 处并回归全部协议。
  - 关系：R2 细化它的作用域；R5 限定内置目录只做模板。
  - 例：新增“示例厂商A”，协议 `proto-a`，地址 `https://api.example-a.test/v1`，模型 `chat-small`，不改代码即可选中。

- **R2 当模型没有声明某参数时，沿“模型 → 厂商 → 全局默认（若有）”向上找；同一键在模型级重新声明时整条定义替换厂商级，不做字段级拼接，否则用户无法撤销上层字段。**
  - 输入：厂商静态参数含 `top_p=0.9`；模型甲声明 `top_p=0.5`；模型乙不声明。
  - 动作：按内部编号查模型定义，有则整条使用，无则用厂商定义；产品若还有全局层，再向上兜底。
  - 结果：模型甲发送 `0.5`；模型乙发送 `0.9`。
  - 理由：字段级深合并会让模型永远带着厂商的附加字段，无法“只删一个”。
  - 关系：为 R6 提供每层的定义；与 R8 的“本层不写”衔接。
  - 例：模型想把 `top_p` 关掉，可声明同键但把该条设为不启用；字段级合并则关不掉。

- **R3 当显示名变化时只改显示名；若必须改内部编号，则在同一保存中改写所有按编号保存的引用并保留凭据账户名，否则偏好与密钥会断链。**
  - 输入：厂商内部编号 `prov-1` 改为 `prov-9`，显示名同步修改。
  - 动作：校验新编号非空且不与现有编号重复；只替换编号字段；把按旧编号保存的偏好改为新编号；凭据账户名保持原值。
  - 结果：模型归属、已保存密钥、偏好继续可用；若旧编号来自内置模板，添加菜单会重新出现该模板。
  - 理由：若凭据账户名由编号推导，改名后按新编号查不到旧密钥，用户会以为密钥丢失并重复输入；若允许重名，按编号查找先命中旧条目，保存新条目会覆盖旧条目。
  - 关系：R4 规定密钥与编号解耦；R11 规定加载时如何处理重复编号。
  - 例：`prov-1` 改为 `prov-9` 后，密钥仍从账户 `acct-1` 读取；偏好 `autocompleteVendor` 从 `prov-1` 改为 `prov-9`。
  - 边界：新编号为空、重复或原编号不存在时拒绝并提示；编号未变化时不写盘。

- **R4 当配置需要保存认证信息时，文件只存凭据账户名，密钥本体存系统密钥库；加载时剥离敏感请求头并告警，否则配置一泄露密钥即泄露。**
  - 输入：配置文件的厂商请求头含 `Authorization: Bearer sk-demo`。
  - 动作：收敛时识别敏感头名（`authorization`、`x-api-key`、`api-key`、`x-goog-api-key` 等），从配置删除并记告警；发送时从密钥库取值后注入。
  - 结果：配置文件不含密钥明文；请求仍带正确认证头。
  - 理由：配置文件常被同步、备份、贴进工单；密钥一旦写入就难以撤回。
  - 关系：R3 的凭据账户名独立于编号；R11 的告警收集。
  - 例：文件中的 `authorization` 头被剥离，告警写明“该头已移除，密钥应存密钥库”；发送时由账户 `acct-1` 注入。
  - 边界：只剥离已知敏感头名；普通头（如 `x-trace-id`）保留。敏感头名单需按目标厂商补充。

- **R5 当应用升级或首次运行时，内置目录只作“添加厂商”的模板，不自动写入用户配置，也不清理用户已有条目，否则升级会凭空多出不可用条目或删掉用户自定义。**
  - 输入：首次运行且配置文件不存在；或新版本内置目录新增、删除条目。
  - 动作：首次运行写入空厂商列表；内置目录只在用户点击“添加”时复制一份；已有用户条目原样保留。
  - 结果：新用户看到空列表和添加入口；老用户配置不因升级改变。
  - 理由：自动灌入模板会产生一批没有密钥、无法使用的条目；自动清理会删除用户手工调过的参数。
  - 关系：R1 的数据驱动；R11 的“读取失败不覆盖”。
  - 例：升级后内置目录新增“示例厂商B”，老用户列表不变，添加菜单里多出该项。

### 3.3 规则组 B：补丁计算

- **R6 当解析一次请求时，按“厂商静态参数 → 模型静态参数 → 当前档位 → 兜底字段”的固定顺序覆盖，顺序不随入口变化，否则设置页预览与真实请求会不一致。**
  - 输入：厂商 `top_p=0.9, frequency_penalty=0.2`；模型 `top_p=0.5`；当前档位写入 `reasoning.depth="high"`；兜底字段 `temperature=0.3`。
  - 动作：先按键合并厂商与模型的静态参数定义（模型同键整条替换），再把合并后的静态参数写入补丁；随后写当前档位，最后叠加兜底字段。
  - 结果：`{top_p:0.5, frequency_penalty:0.2, reasoning:{depth:"high"}, temperature:0.3}`。
  - 理由：两个入口各自实现合并时，任何一处顺序不同都会造成“看到的不是发出去的”，排查成本极高。
  - 关系：R2 定义每层取哪份定义；R8 定义空值；R9 定义拦截；R10 定义嵌套。
  - 例：同一份配置在设置页预览与真实请求中得到完全相同的补丁。补丁内容还应参与模型实例的缓存键，否则切换档位会复用旧实例。
  - 边界：补丁为空时直接返回原发送函数，不包装请求。

- **R7 当一个能力需要多档强度时，所有档位共用同一个参数路径、每档只给一个取值，默认档位不存在则取第一档，否则同一阶梯会散成多个键。**
  - 输入：阶梯路径 `reasoning.depth`，档位 `[off:null, low:"low", high:"high"]`，默认档写 `medium`（不存在）。
  - 动作：先找默认档，找不到取第一档；用户选中档位则用该档取值。
  - 结果：未选择时按 `off` 处理，不写入该路径；选择 `high` 时写入 `"high"`。
  - 理由：把参数名也放进档位，会让同一阶梯的键不一致，合并时互相覆盖成随机结果。
  - 关系：R8 的空值语义；R12 的旧格式迁移。
  - 例：选择 `high` 发送 `reasoning.depth="high"`；选择 `off` 不发送该键。
  - 边界：阶梯没有档位或路径为空时整条阶梯无效，加载或表单校验应拒绝。

- **R8 当补丁取值为空时，静态参数表示该条定义不发送、档位表示本档不写入、只有兜底字段表示删除该键；混为一谈会让关闭档位抹掉共享参数，或误以为空值能删除下层。**
  - 输入：厂商静态参数写入 `thinking.level="low"`；当前档位取值为空；兜底字段 `legacy_flag: null`。
  - 动作：静态参数与档位遇空值跳过；兜底字段遇空值删除对应键。
  - 结果：`thinking.level` 仍为 `"low"`；`legacy_flag` 从请求体移除（若存在）。
  - 理由：档位空值的语义是“本档不设置”，不是“替所有层删除”；若当删除处理，关闭思考会顺带删掉厂商共享设置。
  - 关系：细化 R6、R7；与 R10 的嵌套路径配合。
  - 例：档位 `off` 的空值不会删除厂商层写入的 `thinking.level`；若确实要关掉，应把厂商层该参数设为不启用，或删除该定义。
  - 边界：若模型用同键空值覆盖厂商定义，厂商定义在 R2 的整条替换时已被换掉，最终该键不发送——这是“模型没提供该键”，不是空值发起了删除。兜底字段顶层空值删除整个键；对象内部空值在最终合并时删除对应叶子。删除嵌套叶子可能留下空父对象，对多数协议无影响；要求严格时在删除后向上清理空对象。

**R8 的空值语义汇总**：

| 出现位置 | 语义 | 结果 |
|---|---|---|
| 静态参数值为空 | 该条定义不发送 | 若已替换上层同键定义，则整键不发送 |
| 档位取值为空 | 本档不写入 | 其他层写入的同路径值保留 |
| 兜底字段为空 | 删除 | 最终请求体移除该键 |

- **R9 当用户参数试图写入传输层自有键时，跳过并告警而不抛错，否则一次手误就能让请求非法或绕过工具白名单。**
  - 输入：兜底字段含 `messages: [...]`；静态参数含 `tools.0.name`。
  - 动作：取点号路径第一段，命中受保护集合则跳过，告警写明被跳过的键。
  - 结果：请求体仍由传输层生成这些键，用户补丁不含它们。
  - 理由：允许覆盖 `messages` 可篡改对话内容；覆盖 `tools` 可绕过工具白名单。
  - 关系：对 R6 的每一层都适用；R10 的点号路径决定第一段。
  - 例：`messages` 被跳过，告警写明“该键由传输层所有”；其余参数照常合并。
  - 边界：受保护集合必须按目标协议逐项盘点；新增协议时要重新核对，不能照搬。

- **R10 当参数键含点号时点号创建嵌套对象，兜底字段与已有对象同键时递归深合并、叶子整体替换，否则改一个嵌套字段会丢掉同对象的其他字段。**
  - 输入：兜底字段 `{"metadata":{"tier":"fast"},"temperature":0.3}`；补丁中已有 `metadata:{trace:"on"}`（来自静态参数）。
  - 动作：同键对象递归合并；非对象值直接替换；空值删除。
  - 结果：`metadata:{trace:"on",tier:"fast"}`；`temperature` 为 `0.3`。
  - 理由：不深合并时，用户写一个嵌套字段会丢掉同对象下的其他字段；全量替换又无法表达“只改一处”。
  - 关系：R6 的覆盖顺序；R8 的空值删除。
  - 例：`reasoning.depth` 写入 `{reasoning:{depth:"high"}}`，不把 `reasoning` 下其他字段清空（当操作发生在兜底字段上时）。
  - 边界：静态参数与档位走点号覆盖，叶子整体替换，不做对象深合并；只有兜底字段做深合并。

### 3.4 规则组 C：加载与迁移

- **R11 当加载配置时，未知字段静默丢弃、非法条目跳过、重复编号忽略、默认值补齐；需要用户知道的问题记告警，任何情况都不抛错；读取失败不覆盖用户文件，否则一处笔误会让全部模型不可用。**
  - 输入：配置含一个无编号厂商、两个同编号厂商、一个非法协议值、一个不存在的默认模型编号。
  - 动作：未知字段静默丢弃；无编号条目跳过并告警；第二个同编号条目忽略并告警；非法协议回退到默认协议；默认模型不存在则取第一个可用模型。
  - 结果：其余条目可用；需要用户知道的问题逐条写入告警；文件不被自动重写。
  - 理由：手工编辑是产品承诺的一部分，任何一处笔误都不应让整个功能瘫痪；读失败时自动重写会销毁用户唯一副本。
  - 关系：R4 的敏感头剥离；R5 的不清理；R12 的旧格式迁移。
  - 例：`version` 缺失按 1 处理；默认模型指向已删除模型时回退到第一个模型。
  - 边界：文件不存在或为空时写入一次空配置；文件存在但读取异常时只回退内存，不写盘。

- **R12 当格式升级时，只在旧数据能无损表达为新格式时自动迁移；不能无损表达就丢弃并告警，不猜测映射，否则用户以为迁移成功而实际少了参数。**
  - 输入：旧格式的“思考”配置，每个档位引用多个参数键。
  - 动作：检查所有档位是否恰好共用一个非空参数键；是则迁移为“一个路径 + 每档取值”；否则丢弃并告警。
  - 结果：单键旧配置自动可用；多键旧配置得到空档位并提示重新设置。
  - 理由：多键组合无法压进单一路径，强行取其中一个键会静默改变行为。
  - 关系：R7 的单一路径约束；R11 的告警收集。
  - 例：旧档位 `{low:{depth:"min"}, high:{depth:"max"}}` 迁移为路径 `depth`；旧档位 `{low:{depth:"low",budget:1}, high:{depth:"high",budget:2}}` 丢弃并告警。
  - 边界：迁移只为兼容旧版本存在；新格式写入后不再回写旧格式。

### 3.5 把整条流程串起来

启动时先读配置文件，交给收敛函数：坏条目被跳过、默认值补齐、密钥头被剥离，得到一份合法配置与告警列表。用户发起请求时，按内部编号找到厂商与模型，先取厂商静态参数，再用模型静态参数整条替换同键定义，然后取当前强度档位写入单一参数路径，最后叠加模型兜底字段。所有写入都落到同一个补丁对象；空值在静态参数与档位中表示跳过，在兜底字段中表示删除，受保护键一律跳过并告警。补丁算完后交给传输层，与传输层生成的 JSON 请求体深合并，得到最终请求体。设置页预览与真实发送应调用同一个纯函数，才能保证两者一致。

## 4. 实现思路（讲为什么这样组织，不逐行解释）

- **数据怎么放**：三层结构——配置文档（厂商、模型、参数、档位、默认项）、运行时只读快照（加载后供界面与传输层共同读取）、请求补丁（纯函数产出，不持有状态）。这样分开是因为界面与传输层必须看到同一份配置，任何一方各自缓存都会漂移。
- **关键过程怎么走**：加载 → 收敛（R11/R12）→ 发布快照；请求 → 查厂商与模型 → 算补丁（R6–R10）→ 传输层合并 → 发送。改名与密钥路径（R3/R4）与合并逻辑互不影响，单独处理。
- **边界怎么处理**：空补丁直接返回原发送函数；非 JSON 请求体原样放行；受保护键跳过并告警；读失败只回退内存不写盘；文件不存在则写入一次空配置。
- **与规则对应**：R1/R2/R5 对应数据结构与查表；R6–R10 对应补丁函数；R3/R4 对应改名与密钥；R11/R12 对应收敛函数。以下示意代码覆盖补丁部分，已验证与 R6–R10 一致；改名与收敛未画出，避免喧宾夺主。

```ts
// 中性示意：类型与函数名均为自造，不依赖任何外部符号。
type Json = string | number | boolean | null | Json[] | { [key: string]: Json };
type JsonObject = { [key: string]: Json };
type ParamDef = { key: string; value: Json; enabled: boolean };
type Level = { id: string; value: Json | null };
type Ladder = { path: string; default?: string; levels: Level[] };
type Vendor = { id: string; staticParams: ParamDef[]; ladder: Ladder | null };
type Model = { id: string; staticParams: ParamDef[]; ladder: Ladder | null; fallback: JsonObject };

const TRANSPORT_OWNED = new Set(["messages", "model", "stream", "tools", "tool_choice", "input"]);

function isObject(value: Json | undefined): value is JsonObject {
  return typeof value === "object" && value !== null && !Array.isArray(value);
}

// 点号路径建嵌套；空值删除。静态参数与档位只用这一种写入。
function writeAtPath(target: JsonObject, path: string, value: Json | null): void {
  const parts = path.split(".").filter(Boolean);
  if (parts.length === 0) return;
  let cursor = target;
  for (const key of parts.slice(0, -1)) {
    if (!isObject(cursor[key])) cursor[key] = {};
    cursor = cursor[key] as JsonObject;
  }
  const leaf = parts[parts.length - 1];
  if (value === null) delete cursor[leaf];
  else cursor[leaf] = value;
}

// 所有层共用：传输层自有键一律跳过并告警，避免用户参数破坏请求结构。
function applyAtPath(
  target: JsonObject,
  path: string,
  value: Json,
  warnings: string[],
  source: string,
): void {
  if (TRANSPORT_OWNED.has(path.split(".")[0])) {
    warnings.push(`skip transport-owned key: ${path} (${source})`);
    return;
  }
  writeAtPath(target, path, value);
}

// 兜底字段额外支持对象深合并：用户只写一个嵌套字段时不清空同对象。
function mergeAtPath(target: JsonObject, path: string, value: Json): void {
  const parts = path.split(".").filter(Boolean);
  if (parts.length === 0) return;
  let cursor = target;
  for (const key of parts.slice(0, -1)) {
    if (!isObject(cursor[key])) cursor[key] = {};
    cursor = cursor[key] as JsonObject;
  }
  const leaf = parts[parts.length - 1];
  if (value === null) delete cursor[leaf];
  else if (isObject(cursor[leaf]) && isObject(value)) {
    cursor[leaf] = mergeObject(cursor[leaf] as JsonObject, value);
  } else {
    cursor[leaf] = value;
  }
}

function mergeObject(base: JsonObject, patch: JsonObject): JsonObject {
  const out: JsonObject = { ...base };
  for (const [key, value] of Object.entries(patch)) {
    if (value === null) delete out[key];
    else if (isObject(out[key]) && isObject(value)) out[key] = mergeObject(out[key] as JsonObject, value);
    else out[key] = value;
  }
  return out;
}

function pickLevel(ladder: Ladder | null, levelId?: string | null): Level | null {
  if (!ladder || ladder.levels.length === 0) return null;
  const wanted = levelId ?? ladder.default;
  return ladder.levels.find((level) => level.id === wanted) ?? ladder.levels[0];
}

function resolvePatch(vendor: Vendor, model: Model, levelId?: string | null) {
  const patch: JsonObject = {};
  const warnings: string[] = [];
  // 同键后写覆盖先写：先放厂商定义，再放模型定义。
  const defs = new Map<string, ParamDef>();
  for (const def of vendor.staticParams) defs.set(def.key, def);
  for (const def of model.staticParams) defs.set(def.key, def);
  for (const def of defs.values()) {
    if (def.enabled && def.value !== null) {
      applyAtPath(patch, def.key, def.value, warnings, "static param");
    }
  }
  const ladder = model.ladder ?? vendor.ladder;
  const level = pickLevel(ladder, levelId);
  if (ladder && level && level.value !== null) {
    applyAtPath(patch, ladder.path, level.value, warnings, "level");
  }
  for (const [key, value] of Object.entries(model.fallback)) {
    if (TRANSPORT_OWNED.has(key.split(".")[0])) {
      warnings.push(`skip transport-owned key: ${key}`);
      continue;
    }
    mergeAtPath(patch, key, value);
  }
  return { patch, warnings };
}

// 只在发送前合并一次；非 JSON 请求体原样放行，避免破坏流式或二进制上传。
function wrapSend(send: typeof fetch, patch: JsonObject): typeof fetch {
  if (Object.keys(patch).length === 0) return send;
  return (input, init) => {
    if (!init || typeof init.body !== "string" || init.body.length === 0) return send(input, init);
    try {
      const parsed: unknown = JSON.parse(init.body);
      if (!isObject(parsed as Json)) return send(input, init);
      return send(input, { ...init, body: JSON.stringify(mergeObject(parsed as JsonObject, patch)) });
    } catch {
      return send(input, init);
    }
  };
}
```

## 5. 逐步示例（用一份完整输入，一步步走到结果）

**示例输入**：一家厂商、一个模型，用户选择最高档位。

```json
{
  "vendors": [{
    "id": "prov-1",
    "label": "示例厂商A",
    "protocol": "proto-a",
    "staticParams": [
      { "key": "top_p", "value": 0.9, "enabled": true },
      { "key": "frequency_penalty", "value": 0.2, "enabled": true },
      { "key": "vendor_note", "value": null, "enabled": true }
    ],
    "ladder": {
      "path": "reasoning.depth",
      "default": "low",
      "levels": [
        { "id": "off", "value": null },
        { "id": "low", "value": "low" },
        { "id": "high", "value": "high" }
      ]
    },
    "models": [{
      "id": "chat-small",
      "label": "小模型",
      "staticParams": [{ "key": "top_p", "value": 0.5, "enabled": true }],
      "ladder": null,
      "fallback": {
        "temperature": 0.3,
        "metadata": { "tier": "fast" },
        "legacy_flag": null
      }
    }]
  }]
}
```

传输层原始请求体（由传输层生成）：

```json
{ "model": "chat-small", "messages": [{ "role": "user", "content": "你好" }], "stream": true, "temperature": 0.7, "metadata": { "trace": "on" } }
```

### 步骤 1 · 收敛配置

- 依据：R11、R12。
- 操作：读取并收敛。所有条目都有编号；协议 `proto-a` 合法；配置未写默认模型；档位默认 `low` 存在。
- 结果（中间态）：默认模型回退为第一个模型 `chat-small`；其余字段原样保留；告警为空。`vendor_note` 的值为空，加载后仍是合法条目（空值在合并阶段才决定跳过）。
- 说明：收敛只保证结构合法，不改变业务取值。

### 步骤 2 · 取厂商与模型定义

- 依据：R2。
- 操作：按内部编号找到 `prov-1` 与 `chat-small`；模型级 `top_p` 与厂商级同键，整条替换。
- 结果（中间态）：静态参数定义变为 `top_p=0.5`、`frequency_penalty=0.2`、`vendor_note=null`；阶梯因模型未声明而继承厂商的 `reasoning.depth`。
- 说明：`top_p` 只保留模型那份定义，不做 0.9 与 0.5 的字段级拼接。

### 步骤 3 · 写入静态参数

- 依据：R6、R8。
- 操作：遍历静态参数，启用的且值非空的写入补丁。
- 结果（中间态）：`{top_p:0.5, frequency_penalty:0.2}`；`vendor_note` 因值为空被跳过，且不会产生“删除”动作。
- 说明：静态参数的空值是“本层不发送”，不是删除。

### 步骤 4 · 写入当前档位

- 依据：R6、R7。
- 操作：用户选择 `high`，档位取值 `"high"`，路径 `reasoning.depth`。
- 结果（中间态）：`{top_p:0.5, frequency_penalty:0.2, reasoning:{depth:"high"}}`。
- 说明：点号路径自动创建嵌套对象。

### 步骤 5 · 叠加兜底字段

- 依据：R6、R8、R9、R10。
- 操作：`temperature` 覆盖为 `0.3`；`metadata` 与补丁中不存在的对象直接写入；`legacy_flag` 为空值，执行删除（当前不存在，无变化）。
- 结果（中间态）：`{top_p:0.5, frequency_penalty:0.2, reasoning:{depth:"high"}, temperature:0.3, metadata:{tier:"fast"}}`。
- 说明：兜底字段优先级最高；其中空值是删除语义。

### 步骤 6 · 合并进原始请求体

- 依据：R6、R10。
- 操作：把补丁与传输层原始请求体深合并；同键对象递归合并。
- 结果（中间态）：`temperature` 从 `0.7` 变为 `0.3`；`metadata` 变为 `{trace:"on",tier:"fast"}`；其余键新增。
- 说明：`messages`、`model`、`stream` 未被用户触碰，保持传输层原值。

### 步骤 7 · 最终请求体

```json
{
  "model": "chat-small",
  "messages": [{ "role": "user", "content": "你好" }],
  "stream": true,
  "temperature": 0.3,
  "metadata": { "trace": "on", "tier": "fast" },
  "top_p": 0.5,
  "frequency_penalty": 0.2,
  "reasoning": { "depth": "high" }
}
```

### 反例与边界

- **反例（受保护键）**：兜底字段写成 `{"messages":[…]}` → 该条被跳过并产生告警，最终 `messages` 仍是传输层生成的内容（R9）。
- **反例（重复编号）**：厂商列表出现两个 `prov-1` → 第二个被忽略并告警，只有第一个生效（R11）。
- **反例（配置文件读坏）**：文件存在但读取异常 → 内存回退到空配置并告警，文件不被重写；用户修正文件后重载即可恢复（R11）。
- **边界（关闭档位）**：用户选择 `off`（值为空）→ 不写入 `reasoning.depth`；若厂商静态参数已写入 `reasoning.depth="low"`，该值会保留而不被删除（R8）。
- **边界（嵌套删除）**：兜底字段写 `{"metadata":{"tier":null}}` → 最终请求体中 `metadata.tier` 被删除，`metadata` 下其他叶子保留（R8、R10）。
- **边界（空父对象）**：删除 `reasoning.depth` 时若 `reasoning` 原本不存在，可能留下 `reasoning:{}`；对多数协议无影响，要求严格时在删除后向上清理空对象（R8）。

## 6. 为什么有效，什么时候失效

- **有效的原因**：配置与代码分离后，新增厂商只动数据；合并是纯函数，界面与传输层可复用同一份实现，预览与实发不会各算一套；宽容收敛把“坏输入”变成“可用输入 + 告警”，避免单点故障扩散；密钥与配置分离，泄露面从“整份配置”缩到“系统密钥库”。
- **失效的前提**：
  - 请求体不是 JSON 对象（二进制上传、表单、gRPC）。此时无法在 HTTP 请求体上做键值合并，必须把合并点下移到适配器的结构化字段。
  - 厂商差异无法用“键 + 值”表达（签名算法、握手流程、流式事件格式不同）。这些仍需协议适配器代码，R1 的“零代码”承诺不成立。
  - 一个档位无法压成单一参数路径（例如“开关 + token 预算”必须成对出现）。单阶梯表达不了，需要模板变量或专用字段。
  - 配置只有一个写者。多进程或多人同时编辑需要文件锁或合并策略，R11 的“读失败不覆盖”不足以保证一致。
  - 系统提供可用的密钥库。无密钥库环境要换成环境变量或外部密钥服务，R4 的存储位置改变，其余规则不变。
  - 内部编号由本系统掌控。若编号由外部系统同步，R3 的改名迁移必须同步外部，否则引用会断。
- **失效后要改哪几条**：R1（适配器边界）、R6（合并位置）、R7（多参数档位）、R4（密钥来源）、R3（编号所有权）。
- **已知取舍**：放弃“任意厂商零代码”的绝对承诺，只覆盖同一协议族；换来可测试、可预览、用户可自行扩展的配置能力。

## 7. 常见误区

- **误区：把密钥写进配置文件。**
  - 后果：配置随备份、截图、工单附件泄露，密钥难以撤回。
  - 正确做法：只存凭据账户名，发送时从密钥库注入（见 R4）。
- **误区：用显示名做引用键。**
  - 后果：改名后偏好与密钥断链，用户看到“未配置密钥”或默认项失效。
  - 正确做法：引用一律记内部编号，改名时迁移所有按编号保存的引用（见 R3）。
- **误区：不同层之间做字段级深合并。**
  - 后果：模型永远带着厂商的附加字段，无法撤销。
  - 正确做法：同键整条替换，只保留一份定义（见 R2）。
- **误区：坏配置抛异常或自动重写。**
  - 后果：一处笔误让全部模型不可用，或把用户唯一副本抹掉。
  - 正确做法：收敛为告警，读失败不写盘（见 R11）。
- **误区：把空值统一当删除。**
  - 后果：关闭档位时抹掉厂商共享参数，行为超出用户预期。
  - 正确做法：静态参数与档位的空值是“本层不写”，只有兜底字段的空值才删除（见 R8）。
- **误区：旧格式猜测映射。**
  - 后果：静默丢失参数，用户以为迁移成功。
  - 正确做法：能无损才迁移，否则丢弃并告警（见 R12）。
- **误区：把内置目录自动写入用户配置。**
  - 后果：升级凭空多出不可用条目，或清理掉用户自定义。
  - 正确做法：内置目录只做添加模板（见 R5）。
- **误区：受保护键没有白名单。**
  - 后果：用户覆盖 `messages` 或 `tools`，请求非法或绕过工具白名单。
  - 正确做法：按协议盘点受保护键，命中即跳过并告警（见 R9）。
- **误区：合并顺序随入口变化。**
  - 后果：设置页预览与真实请求不一致，排查成本极高。
  - 正确做法：只保留一个纯函数，所有入口共用（见 R6）。
- **误区：模型实例缓存键不含补丁。**
  - 后果：切换强度档位后仍复用旧实例，参数不生效。
  - 正确做法：把解析后的补丁内容纳入缓存键（见 R6）。

## 8. 迁移到其他产品形态

- **不变的部分**：配置文档、作用域链、固定合并顺序、空值分层语义、受保护键、宽容收敛、密钥与配置分离。
- **必须改的部分**：协议适配器（选择哪种传输）、受保护键集合（按目标协议）、密钥存储（密钥库、环境变量或密钥服务）、配置存储（文件、数据库或远端）、旧格式迁移策略。
- **改动清单**：
  1. 列出目标协议由传输层自有的键，形成受保护集合。判定标准：用户覆盖后会导致请求非法或越过安全边界。
  2. 确认请求体是 JSON 对象；不是则把合并点从 HTTP 请求体下移到适配器的结构化字段。判定标准：发送前能否拿到可读写的对象。
  3. 盘点厂商差异：能表达为“键 + 值”的进配置；涉及签名、握手、事件格式的留在适配器。判定标准：是否需要执行代码而不只是读值。
  4. 选择密钥存储，并保留“凭据账户名”这一层间接引用。判定标准：更换存储时配置文档是否需要改。
  5. 定义旧格式迁移的无损判定。判定标准：旧数据能否一对一映射到新结构。
- **迁移假设**：目标产品同样需要用户可配多厂商，且协议数量可控在少数适配器内；若厂商协议差异极大或需要任意脚本，应改为插件式适配器，R1 的“零代码”承诺失效。

## 9. 验证清单

> 每条规则给正、反、边三例，写明期望输出与副作用。示例值全部为假想；外部事实见 §0.1（真实、带来源与核实状态）。

**R1**
- 正：配置新增 `prov-2`（`proto-a`，含 `chat-large`）→ 重载后可选中；代码无新增厂商名。
- 反：只加代码适配器分支、不加配置 → 选择器不出现该厂商，用户无法使用。
- 边：已有厂商追加模型 → 仅配置变更，模型可用，其他模型不受影响。

**R2**
- 正：厂商 `top_p=0.9`，模型声明 `top_p=0.5` → 最终发送 `0.5`。
- 反：模型未声明 → 继承厂商值 `0.9`。
- 边：模型声明同键但设为不启用 → 不发送 `top_p`，且不回退到厂商值。

**R3**
- 正：`prov-1` 改为 `prov-9`，凭据账户 `acct-1` 保留，偏好改写 → 旧密钥仍可用。
- 反：新编号为空或与现有编号重复 → 拒绝并提示，配置不变。
- 边：新编号与旧编号相同 → 不写盘、不产生告警。

**R4**
- 正：配置含 `authorization` 头 → 加载后该头被剥离并告警，发送时从密钥库注入。
- 反：密钥直接写在文件中 → 检测到敏感头并移除，用户需在密钥库重填。
- 边：非敏感头 `x-trace-id` → 保留，不告警。

**R5**
- 正：首次运行且无文件 → 写入空厂商列表，添加菜单含内置模板。
- 反：升级后内置目录新增条目 → 用户列表不变，仅在添加菜单出现。
- 边：用户从模板添加一家厂商 → 生成副本，后续模板变更不影响已添加条目。

**R6**
- 正：四层同键依次覆盖 → 最终值等于最后一层。
- 反：某个入口按“兜底 → 档位 → 模型 → 厂商”合并 → 预览与实发不一致，应禁止。
- 边：某层为空 → 跳过，不影响其他层；补丁为空 → 返回原发送函数。

**R7**
- 正：默认档位不存在 → 取第一档。
- 反：每档各写不同参数名 → 同一阶梯写入多个键，行为不可预期，应拒绝。
- 边：阶梯没有档位 → 视为无阶梯，不写任何键。

**R8**
- 正：档位为空且厂商已写同名键 → 厂商值保留。
- 反：把档位空值当删除 → 厂商共享参数被抹掉，属错误实现。
- 边：模型用同键空值覆盖厂商静态参数 → 整键不发送（R2 替换），不视为删除其他层。

**R9**
- 正：兜底字段写 `messages` → 跳过并告警，传输层消息不变。
- 反：不设保护 → 用户覆盖 `messages`，对话内容可被篡改。
- 边：写 `tools.0.name` → 第一段 `tools` 命中，整条跳过。

**R10**
- 正：`reasoning.depth` → 生成嵌套对象，而不是字面键 `"reasoning.depth"`。
- 反：把点号当普通字符 → 厂商收到不认识的键，参数不生效。
- 边：兜底对象与已有对象同键 → 深合并，未提及的叶子保留。

**R11**
- 正：一个无编号厂商加一个合法厂商 → 前者跳过并告警，后者可用。
- 反：抛异常终止 → 全部模型不可用。
- 边：配置文件读取失败 → 内存空配置加告警，文件不被重写。

**R12**
- 正：旧档位共用一个参数键 → 自动迁移为该键的取值阶梯。
- 反：旧档位引用两个参数键 → 丢弃并告警，要求重新配置。
- 边：旧配置没有档位 → 视为无阶梯，不生成空壳配置。
