# 无边框窗口边缘交互按「阀段 + 原生 resize」分流
- 日期：2026-11-08
- 状态：已采纳
- 关联约束：INV-018、INV-019
- 关联坑点：pitfalls/2026-11-08-最大化后四角点击穿透.md

## 背景

Windows/Linux 是无边框透明窗口（`decorations:false` + `transparent:true`），窗口外观与命中全靠自绘。用户报告了两个边缘问题：

1. 最大化后四角是透明圆弧，点击穿透到下层窗口（坑点，见 pitfalls）；
2. 拖动左右边框时意图歧义：可能是想调整窗口宽度，也可能是想打开/关闭/拖动侧栏（左：资源管理器侧栏；右：AI 面板）——侧栏收起时其 `ResizableHandle` 恰好贴在窗口边缘且通栏全高，整条边框都被侧栏操作占用，只有 tao 原生的最外圈约 4px 能调整窗口。

产品同时要求窗口控制按钮「显示要小、点击区域要大」，点击区通栏标题栏且不留真空像素。这三件事的共同约束是：**自绘边框必须在原生窗口行为的缝隙里设计**（tao 在非最大化时于 `WM_NCHITTEST` 提供 `SM_CXFRAME` 外圈原生 resize，最大化时取消；webview 收不到非客户端区域的指针事件，见 INV-019）。

## 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A（最终采用）：非最大化时只有边框上的「阀段」（垂直居中 96px 小段）执行侧栏开/关/拖动，其余边框区域调 `startResizeDragging` 交还系统 resize；最大化时整条边框统一执行侧栏操作 | 边框默认语义是调整窗口，符合桌面窗口惯例；侧栏仍保留可发现的边缘入口（悬停竖条握把）；最大化时 resize 无意义，语义整体让渡给侧栏，正好复用同一套阀逻辑 | 阀段有发现成本，靠悬停握把补偿；实现需感知最大化状态（`useWindowMaximized`）并处理 `zoom-content` 缩放换算 |
| B：整条左右边框始终执行侧栏操作（收起态 handle 的自然延伸） | 实现最简单，无需新组件 | 非最大化时用户无法从左右边框调整窗口宽度，与所有桌面应用的窗口惯例冲突，歧义依旧 |
| C：边框全部窗口 resize，侧栏只留面板间内部分隔线 | 语义最简单，无新概念 | 侧栏收起后失去从边缘展开的入口，违背「边框区域任何像素都要能点击、不能真空」的产品要求 |

## 结论与理由

采用 A。核心原则：**非最大化时把边框还给窗口惯例（resize），最大化时把边框让渡给侧栏（resize 本就不存在）**。同一分流逻辑天然覆盖两个窗口状态，且 `startResizeDragging` 是 Tauri core API，无需自绘 resize 循环。窗口控制按钮与四角直角遵循同一原则的另外两面：命中区服从原生窗口几何（按钮贴右缘、最大化四角直角），视觉服从产品要求（图标小、圆角仅非最大化）。

未来重新评估的条件：
- tao/Tauri 为 undecorated 窗口提供可配置的原生 resize 边框宽度或官方 edge-zone API 时，webview 侧分流可以简化；
- 产品若把侧栏展开入口改为按钮/快捷键主导，可去掉阀段、回归方案 C；
- 若用户反馈阀段发现成本过高，可考虑阀段加常显握把或扩大阀段高度。
