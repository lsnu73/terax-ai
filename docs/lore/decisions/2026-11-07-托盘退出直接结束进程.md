# 托盘「关闭程序」直接结束进程，不依赖前端存活
- 日期：2026-11-07
- 状态：已采纳
- 关联约束：无
- 关联坑点：无

## 背景
关闭方式支持「缩小到托盘」后（2026-11-06 上线），托盘右键菜单提供「关闭程序」。菜单事件发生在 Rust 侧，而完整的收尾流程（AI 会话落盘 `flushSessionWrites`、忙碌终端与脏编辑器确认）都住在前端关闭守卫 `useAppCloseGuard` 里。托盘是窗口隐藏后用户唯一的图形入口，它的退出动作必须无条件可用。

## 候选方案
| 方案 | 优点 | 缺点 |
|---|---|---|
| A（最终采用）：Rust 菜单事件里直接 `app.exit(0)` | 不依赖前端存活：页面挂死、尚未启动、热重载中都能退出；实现只有一行 | 绕过落盘守卫与脏编辑器确认；最后一次未落盘的会话写入依赖流式中途定时保存（最长 2 秒间隔） |
| B：菜单事件转发前端，走与窗口关闭相同的 `finishClose` | 两条退出路径行为完全一致，落盘有保障 | 前端挂死或未启动时托盘退出失效，托盘反而变成「退不掉」的入口；需要新增专用 IPC 与超时兜底，复杂度不成比例 |
| C：菜单只留「打开」，去掉「关闭程序」 | 无数据风险 | 用户只能任务管理器杀进程，比 A 的数据代价更差 |

## 结论与理由
采用 A。托盘的存在意义是「窗口不可达时的最后入口」，退出路径必须无条件可用；完整守卫已经在窗口关闭按钮那条路径上承担（含 4 秒落盘超时与一次「仍然关闭」确认）。选择「缩小到托盘」驻留的用户在关闭窗口时已确认过一次驻留意图，AI 会话流式中途每最多 2 秒自动落盘一次，极端情况下的丢失窗口很小。

未来重估条件：若会话持久化整体下沉到 Rust 侧，或产品要求托盘退出同样走忙碌/脏确认，应把「关闭程序」接到与窗口关闭相同的守卫上，并为此增加前端不可用时的超时强制退出兜底。
