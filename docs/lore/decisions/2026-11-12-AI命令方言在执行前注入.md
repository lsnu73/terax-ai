# AI 命令方言在执行前注入

- 日期：2026-11-12
- 状态：已采纳
- 关联约束：INV-021

## 背景

Windows 本地工作区中，AI 曾把 `echo "$PATH" | tr ... | grep ...` 交给 PowerShell，失败后才改用 `$env:PATH` 和 `Where-Object`。这多出一次工具往返并浪费 token。当时 `<env>` 只有路径，工具名与系统提示词又使用 `bash_run`，模型没有可靠的实际方言信息。

## 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| 执行前注入真实 Shell 元数据，并动态生成工具描述（最终采用） | 首次调用前即可约束方言；覆盖 full/lite/custom 提示词；不增加模型探测往返 | 需要把原生描述传入本轮工具构建链 |
| 只在内置系统提示词中写 Windows 规则 | 修改最少 | 用户覆盖或 custom 提示词会绕过；Local/WSL 切换时静态规则容易失真 |
| 失败后自动翻译并重试 | 表面上减少用户感知到的失败 | 引号、管道、重定向和退出码语义不同，可能改变命令含义；还会产生非用户请求的重试 |
| 增加 Shell 探测工具让模型先调用 | 无需扩展 transport | 每次任务多一次模型工具往返，本身消耗 token |

## 结论与理由

采用执行前注入。`shell_describe` 只读取配置和文件存在性，不启动 Shell；每轮 `<env>` 与工具描述使用其返回值，模型第一次构造命令就有明确约束。失败时只附加方言提示，保留原始输出，不自动翻译或重试。

动态信息不能写入 stable system prompt，否则 Local/WSL 切换会改变稳定前缀并影响提示词缓存。每次工具执行捕获同一个 `WorkspaceEnv` 快照，避免 describe/open/run/spawn 分别读取 store 时跨工作区漂移。

未来若工具协议原生支持结构化执行环境，或 AI Shell 改为长期存活的单一解释器，可重新评估当前元数据传递链；若支持自动命令转换，必须另有可验证的语法转换层和明确的用户授权，不能把本决策当作允许静默重试。
