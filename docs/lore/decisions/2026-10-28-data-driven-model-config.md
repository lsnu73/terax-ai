# 模型配置改为数据驱动：结构化参数声明 + 原始 JSON 逃生口
- 日期：2026-10-28
- 状态：已采纳
- 关联约束：INV-003、INV-004、INV-005、INV-006
- 关联坑点：pitfalls/2026-10-28-models-json-no-reload.md

## 背景

旧实现把 13 家国外厂商、全部模型、上下文/价格/能力数据硬编码在 `src/modules/ai/config.ts`，请求参数也按厂商写在代码分支里。新需求要求：

1. 厂商切换为国内厂商；
2. 模型列表不再硬编码，能拉 `/models` 的拉取、不能拉的手动添加；
3. 厂商请求参数名与思考取值没有标准，必须可动态增删、可表达映射；
4. 所有配置落到可手改的 JSON，UI 与手改等价；
5. API Key 继续只存钥匙串；
6. 新增 Provider 对核心代码侵入接近零。

难点是「参数名不可硬编码」与「滑块要表达厂商差异」同时成立：只做键值合并无法表达“关闭思考要同时改 `thinking.type` 并省略 `reasoning_effort`”，也无法表达 `medium → high` 的归一化。

## 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A（最终采用）：结构化 `ParamDef`（键/位置/路径/类型/枚举/默认值/映射）+ 模型级 `extra` 原始 JSON 覆盖 | UI 可读档位、可校验；厂商归一化写在配置的 `map` 里；未知字段仍有逃生口；核心代码零厂商分支 | 配置结构比纯键值合并复杂；需要一套 normalize/merge 引擎与测试 |
| B：只支持「附加一段 JSON」合并 | 实现最小；用户自由度最高 | 无法驱动滑块档位/标签；无法做取值映射与类型校验；关闭思考这类多键联动只能让用户自己写；header 参数无法表达 |
| C：每家厂商一个代码分支 + 参数名写在 adapter 里 | 类型最直观 | 正是需求要消除的硬编码；新增厂商要改核心文件并发版 |
| D：动态加载第三方 provider 插件包 | 扩展性最强 | 桌面端插件签名/沙箱/版本兼容成本远超当前需求；国内厂商几乎都是 OpenAI 兼容 |

## 结论与理由

选 A。它把「厂商差异」表达为数据，把「协议差异」压缩为一个封闭的 `protocol` 枚举：

- `config/params.ts` 定义合并顺序（Provider 默认 < Model 默认 < 当前思考档位 < `extra`）、点号嵌套路径、`map` 归一化、`null` 省略、保护键。
- `agent.ts` 只按 `protocol` 选择 adapter；参数注入由 `withRequestParams()` 在 SDK 序列化后的 JSON 上完成，因此源码中不出现任何厂商参数名。
- 新增一家 OpenAI 兼容厂商只需一条 JSON；只有非 OpenAI 协议才需要新增 adapter。

**未来什么条件下应重新评估**：

- 如果出现厂商要求非 JSON 的请求体（如私有二进制协议/特殊流式封装），应新增 `protocol` adapter，而不是把参数塞进 `extra`；
- 如果 `ParamDef` 继续膨胀到需要嵌套条件（“A 为真时才发送 B”），应升级为声明式 JSON Schema 或小型表达式，而不是在 `params.ts` 里写厂商 if；
- 如果用户需要在两个 Provider 下使用同名模型 ID，应把全局唯一 ID 改为 `providerId:modelId` 复合键，届时会影响选择器、收藏、默认模型的存储格式。
