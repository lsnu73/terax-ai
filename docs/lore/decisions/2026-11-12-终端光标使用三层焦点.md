# 终端光标使用三层焦点

- 日期：2026-11-12
- 状态：已采纳
- 关联约束：INV-022

## 背景

终端光标需要在实际聚焦时显示并按用户设置闪烁，在 AI Composer、搜索框或其他控件获得键盘焦点后隐藏。原有 surface 只有原生窗口焦点和标签内逻辑活动窗格：AI 输入框聚焦时原生窗口仍然聚焦，活动窗格也不会变化，因此这两个状态不足以决定光标是否应显示。

## 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| 原生窗口、逻辑活动窗格、真实 textarea 焦点三层门控（最终采用） | 能区分应用内焦点转移；不改变现有 pane pacing；两种渲染器可复用同一条件 | 需要把输入控制器的 focus/blur 接到 surface |
| 只使用原生窗口与逻辑活动窗格 | 修改最少 | AI 或搜索框聚焦时仍显示并闪烁光标 |
| textarea blur 时直接把逻辑 `focused` 改为 false | 不新增状态 | 混淆 activeLeafId 与 DOM 焦点，改变 frame pacing；块编辑器等既有交互会被误判为非活动窗格 |
| blur 时修改 Ghostty 光标设置或 DECTCEM | 表面上复用原生光标状态 | 把 UI 焦点写入终端模型，恢复时难以区分用户设置、Shell 控制序列和焦点状态 |

## 结论与理由

采用三层门控，焦点只影响 presentation，不改写 Ghostty 模型。`focused` 继续表示标签内活动窗格并服务 frame pacing；新增 `inputFocused` 只表示真实键盘焦点；`windowFocused` 继续处理应用级焦点。三者与原生光标可见性、用户闪烁设置和当前闪烁相位共同决定绘制与定时器。

AI 面板打开通过 Composer 挂载聚焦接管键盘输入，关闭通过可见性边界恢复当前活动终端，不在每个按钮和快捷键入口分别实现焦点逻辑。延迟帧必须可取消，避免快速开关后反向抢焦。

未来若应用建立统一、可查询的焦点管理器，或 Ghostty 原生提供与应用 DOM 焦点一致的呈现契约，可重新评估三层状态的承载位置；在语义未统一前不得把真实 DOM blur 直接写成逻辑活动窗格失焦。
