# WSL 命令块分隔线落到下一提示符之后
- 首次出现：2026-11-11
- 影响范围：Windows 上所有以 WSL 工作区创建的 zsh、bash、fish 终端
- 复现条件：在 WSL 终端执行一条有输出的命令，观察输出与下一提示符之间的块尾分隔线

## 表象

Windows 本地终端的分隔线位于命令输出之后、下一提示符之前；WSL 中同一位置没有分隔线，分隔线反而出现在下一待输入提示符之后。OSC 133 命令边界仍然存在，因此问题容易被误判为前端分隔线坐标错误。

## 根因

前端始终以 `blocks=true` 请求 PTY，但 Windows 的 WSL 启动分支丢弃了 `blocks`，`build_wsl` 没有设置 `TERAX_BLOCKS=1`。`wsl.exe` 不默认转发 Windows 进程环境，Shell 因此仍发送 OSC 133 A/B/C/D，却跳过提示符前的一至两行间隔。前端按既有间隔契约计算分隔线位置，最终把它画到下一提示符之后。

## 已采用的修复

`shell_init.rs` 将 `blocks` 传入 `build_wsl`，设置 `TERAX_BLOCKS=1`，并通过 `WSLENV` 的 `TERAX_BLOCKS/u` 显式转发。`TERAX_TERMINAL/u` 一并纳入，因为 fish 等集成入口同样依赖它。`wslenv_with_terax` 统一合并终端集成与代理 token，保留并去重用户已有 `WSLENV`。不修改 OSC 133 解析或前端分隔线公式。

## 复发防护

`shell_init.rs` 的三个 `wslenv_*` 单元测试锁定块模式开关、已有 token 去重和代理 token 保留。新增 WSL 终端变量时必须同时检查变量值与对应 `/u` token；只设置 `CommandBuilder.env` 不会把变量带入发行版。手工回归应覆盖首个提示符、有输出与无输出命令、连续多条命令。
